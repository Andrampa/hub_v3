DIEM EVE flood monitoring · operational

How a daily satellite image becomes a dekadal flood table

A daily job turns each NOAA VIIRS composite into an Earth Engine asset. Once per dekad, EVE combines them into one flood raster, counts what was flooded in every district and appends the result to ArcGIS Online, where the EVE web app and the DIEM Hub read it.

Daily input, dekadal product

NOAA releases a new five-day composite every day. VIIRS_process names each asset by the day it ran, not by the last day of its window. EVE runs on the same triggers but only acts when a dekad has closed and is not yet published. Stage A picks the two or three composites for that dekad from a fixed calendar CSV and keeps, per pixel, the class with the highest priority.

Late or missing days

Both jobs are triggered every hour from 07:00 to 12:00. Every step skips output that already exists, so a retry only does the missing work. A day that never arrives makes Stage A fail on the missing asset. An operator then reprocesses that day or month with VIIRS_process and reruns EVE. Nothing alerts automatically: the logs on the server are the evidence.

One row marks a dekad published

Stage E appends the ADM2, ADM1 and ADM0 rows only if the dekad is absent, then writes the dekad into eve_app_config. The next run reads that row and stops. The web app takes its list of periods from the same table, so a dekad appears in the app only once all its rows exist. ADM1 and ADM0 percentages are recomputed from summed counts, not averaged.

Handoff to the Hub

The DIEM Hub reads the distinct iso3_code values in eve_mastertable_adm0. A country with at least one row gets an EVE link on its country page, opening diem-eve.apps.fao.org in Overview mode. The Flood services page links to the same app. Which countries appear is therefore set by the Stage C ISO3 list in default.yaml.
